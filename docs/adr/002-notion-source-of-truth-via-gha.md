# ADR-002: Notion as content source-of-truth via GitHub Actions sync

**Status:** Proposed (v2 — refined per author feedback)
**Date:** 2026-05-05
**Deciders:** Ernesto Cobos

## v2 changes from initial proposal

1. Cron frequency: every 30 min → **twice a day at 7am + 7pm Mexico CT** (13:00 / 01:00 UTC).
2. Status state machine: `Published` is now **set by the bot**, not the user. User sets `Ready to publish`, bot publishes and flips status. Verifying `Status=Published` in Notion = proof the post is live.
3. Drop `.notion-sync.json` change tracking — the `Ready to publish` status IS the change signal. To re-publish an existing post, flip its status back to `Ready to publish`.

## Context

Today the blog content lives in `content/blog/<slug>/{en.md, es.md}` committed to the repo. EN is the source-of-truth (hand-edited markdown), ES is auto-generated by `scripts/translate-posts.mjs` at `prebuild` time, hash-cached in `content/blog/.translator-cache.json`.

Authoring flow today: edit `.md` in VSCode → `git commit` → `git push` → Vercel deploys.

Two pain points worth fixing:

1. **Authoring UX**: Markdown in VSCode is fine for code-block-heavy posts, but Notion offers a much better editor for prose (mobile, collaborators, drafts, comments, scheduled publish). The user already drafts posts in Notion.
2. **Build coupling**: `prebuild` runs the translator script, which historically ate ~9 min per build before the cache+parallelization fix (PR #6). Even now at 30s steady state, the translator depends on AI Gateway being up during a Vercel deploy. Decoupling means Vercel deploys are pure compile work — predictable and fast.

User constraints (verbatim):
- "Vercel build queda en ≤30s"
- "GitHub descargue el post lo agregue haga el commit a main en automatico"
- "evitar los costos mas caros que son los de vercel"
- Simple y rápido, sin stack exótico.

## Decision

Add a **GitHub Actions workflow** that runs on a 30-minute cron + manual `workflow_dispatch`, fetches Published posts from a Notion database, converts each to markdown, runs the existing `translate-posts.mjs` to generate ES, and commits the result to `main`. Vercel deploy on `main` push runs only the cheap `next build` step.

```
┌──────────┐  cron 30m   ┌──────────────┐  fetch    ┌────────────┐
│  Notion  │◀────────────│ GHA workflow │──────────▶│ Notion API │
└──────────┘             │  sync-notion │           └────────────┘
                         │              │
                         │  ┌────────┐  │
                         │  │ notion │  │ → en.md
                         │  │  -to-  │  │
                         │  │   md   │  │
                         │  └────────┘  │
                         │      │       │
                         │      ▼       │
                         │  translate-  │ → es.md + cache update
                         │  posts.mjs   │
                         │              │
                         │  git commit  │
                         │  git push    │
                         └──────┬───────┘
                                │
                                ▼
                         ┌──────────────┐  webhook    ┌──────────┐
                         │  GitHub main │────────────▶│  Vercel  │ ≤30s
                         └──────────────┘             │ next build│
                                                     └──────────┘
```

`translate-posts.mjs` is REMOVED from `prebuild`. It still lives in `scripts/` for local use (`pnpm run translate`) and is the second step of the GHA workflow.

## Options Considered

### Option A: Cron-polled GHA workflow (RECOMMENDED)

GHA runs every 30 min. Fetches Notion, detects changes via `last_edited_time`, translates, commits. Optional `workflow_dispatch` button for "publish now" if impatient.

| Dimension | Assessment |
|---|---|
| Complexity | Low — one YAML file, one fetch script, reuses existing translator |
| Cost | $0. GHA free tier: 2000 min/mo on personal accounts. Cron 48 runs/day × ~30s = ~24 min/day = ~720 min/mo |
| Latency (publish → live) | Worst case 30 min cron + ~3 min run + ~30s deploy = ~33 min |
| Reliability | High — cron is dead simple, retries automatic next run |
| Vendor lock-in | Notion API (free) + GitHub Actions (already using) |

**Pros:**
- No extra services, no webhook receivers, no relays
- `workflow_dispatch` covers the "I want to publish NOW" case
- Cron acts as safety net — if a manual run fails, next cron picks it up
- Free tier comfortably handles 1 author × few posts/month

**Cons:**
- Up to 30 min latency for unattended publishes — fine for a blog, not for a news site
- 48 wasted runs/day when nothing changed (each ~30s of GHA time)

### Option B: Notion webhook → GHA workflow_dispatch (paid Notion or relay)

Notion webhook (Notion+ plan or via Pipedream/Zapier free tier) hits a GHA `workflow_dispatch` endpoint. Same fetch+translate+commit flow.

| Dimension | Assessment |
|---|---|
| Complexity | Med — requires webhook setup + signature verification |
| Cost | $0 if using free Pipedream tier; otherwise Notion+ at $10/mo |
| Latency | <1 min from publish → live |
| Reliability | Webhook delivery isn't guaranteed; need a fallback cron anyway |
| Vendor lock-in | Adds Pipedream OR Notion paid tier dependency |

**Pros:**
- Near-instant publish
- Zero wasted runs

**Cons:**
- More moving parts (webhook receiver, signature verify, replay protection)
- Still need a cron fallback for missed webhooks → same complexity as A plus the webhook
- For a personal blog at 1-2 posts/month, a 30-min latency is invisible

### Option C: Manual `workflow_dispatch` only (no automation)

User clicks a button in GHA when ready to publish. Same flow, no cron.

| Dimension | Assessment |
|---|---|
| Complexity | Lowest |
| Cost | $0 |
| Latency | Whenever the user clicks |
| Reliability | High — only runs when intended |

**Pros:**
- Maximum control
- Zero idle runs

**Cons:**
- Requires manual step every publish — same friction as today's `git push`, just on a different surface (Notion → GHA button vs `git push`)

### Option D: Notion API at request time (runtime fetch, ISR)

Each page reads from Notion when requested, cached via Next ISR.

**Rejected outright.** Breaks SSG, runtime depends on Notion being up, slower TTFB, harder to debug. The whole point of this proposal is to keep Vercel deploys fast and content static.

## Trade-off Analysis

| Concern | Option A (cron) | Option B (webhook) | Option C (manual) |
|---|---|---|---|
| Setup time | 1-2h | 3-5h | 30 min |
| Ongoing maintenance | Near zero | Medium (webhook drift) | None |
| User effort per publish | Zero | Zero | One button click |
| Latency floor | 30 min worst | <1 min | Instant when clicked |
| Failure recovery | Auto next cron | Need replay logic | Re-click |

**Recommended: Option A.** For a 1-author personal blog at ~1-2 posts/month, the difference between 30-min latency and 1-min latency is invisible — there's no one waiting for the post to land. The infrastructure simplicity of cron-only beats the complexity of webhook setup. Option A includes `workflow_dispatch` as the manual escape hatch, so we get the best of A and C in one workflow.

## Notion database schema (proposed)

Create a Notion database called **"Blog Posts"** with these properties:

| Property | Type | Required | Notes |
|---|---|---|---|
| Title | Title | yes | Post title (any language — actual locale set by source EN body) |
| Slug | Text (rich_text) | yes | URL slug, e.g. `gitops-regulados`. Validated against `/^[a-z0-9-]+$/` |
| Status | Select | yes | Options: `Draft`, `Review`, `Ready to publish`, `Published`. Sync filters by `Ready to publish`; bot flips to `Published` after successful commit. |
| Category | Select | yes | Options: `gitops`, `migrations`, `finops`, `platform` (matches `PostCategory` type) |
| Date | Date | yes | Publish date (the `date` frontmatter field) |
| Display Date | Text | yes | Human-readable, e.g. `Mar 2026` (the `d` frontmatter field) |
| Read time | Text | yes | `5 min` etc. (the `r` field) — could be auto-computed from word count later |
| Cover URL | URL | no | Optional cover image (the `cover` field) |
| Cover Alt | Text | no | Alt text (the `coverAlt` field) |
| Translator override | Select | no | Options: `(default)`, `claude-sonnet-4-6`, `deepseek-v4-flash`. Sets the optional `translator:` frontmatter field. |
| Last edited time | Last edited time (auto) | yes | Used for change detection between cron runs |

Body of the Notion page = the post content (h2 + paragraphs + code blocks, etc.). Converted to markdown by `notion-to-md`.

### Workflow sketch

```yaml
# .github/workflows/sync-notion.yml
name: Sync from Notion
on:
  schedule:
    - cron: "*/30 * * * *"
  workflow_dispatch:

concurrency:
  group: sync-notion
  cancel-in-progress: false

jobs:
  sync:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v3
        with: { version: 10 }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile

      - name: Fetch published posts from Notion
        env:
          NOTION_TOKEN: ${{ secrets.NOTION_TOKEN }}
          NOTION_POSTS_DB: ${{ secrets.NOTION_POSTS_DB }}
        run: node scripts/fetch-notion.mjs

      - name: Translate (EN → ES) for any new/changed posts
        env:
          AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
        run: node scripts/translate-posts.mjs

      - name: Commit if anything changed
        run: |
          git config user.name "Ernesto Cobos"
          git config user.email "ernesto@cobos.io"
          git add content/blog/
          if git diff --cached --quiet; then
            echo "No changes — nothing to publish."
            exit 0
          fi
          git commit -m "Sync posts from Notion ($(date -u +%Y-%m-%dT%H:%MZ))"
          git push
```

### `scripts/fetch-notion.mjs` sketch

```js
import { Client } from "@notionhq/client";
import { NotionToMarkdown } from "notion-to-md";
import { existsSync, mkdirSync, readFileSync, writeFileSync } from "node:fs";
import path from "node:path";

const notion = new Client({ auth: process.env.NOTION_TOKEN });
const n2m = new NotionToMarkdown({ notionClient: notion });

const SYNC_FILE = "content/blog/.notion-sync.json";
const sync = existsSync(SYNC_FILE) ? JSON.parse(readFileSync(SYNC_FILE, "utf8")) : {};

const { results } = await notion.databases.query({
  database_id: process.env.NOTION_POSTS_DB,
  filter: { property: "Status", select: { equals: "Published" } },
});

let changed = 0;
for (const page of results) {
  const props = page.properties;
  const slug = props.Slug.rich_text[0]?.plain_text;
  if (!slug || !/^[a-z0-9-]+$/.test(slug)) {
    console.warn(`[notion] skipping page ${page.id}: invalid slug "${slug}"`);
    continue;
  }
  // Skip if unchanged since last sync
  if (sync[slug]?.last_edited_time === page.last_edited_time) continue;

  const title = props.Title.title.map(t => t.plain_text).join("");
  const date = props.Date.date.start;
  const d = props["Display Date"].rich_text[0].plain_text;
  const r = props["Read time"].rich_text[0].plain_text;
  const category = props.Category.select.name;
  const cover = props["Cover URL"]?.url ?? null;
  const coverAlt = props["Cover Alt"]?.rich_text[0]?.plain_text ?? null;
  const translator = props["Translator override"]?.select?.name;

  const mdblocks = await n2m.pageToMarkdown(page.id);
  const body = n2m.toMarkdownString(mdblocks).parent;

  const fm = [
    "---",
    `slug: ${slug}`,
    `title: "${title.replace(/"/g, '\\"')}"`,
    `d: "${d}"`,
    `date: "${date}"`,
    `r: "${r}"`,
    `category: ${category}`,
    cover && `cover: "${cover}"`,
    coverAlt && `coverAlt: "${coverAlt}"`,
    translator && translator !== "(default)" && `translator: ${translator}`,
    "---",
    "",
  ].filter(Boolean).join("\n");

  const dir = path.join("content/blog", slug);
  mkdirSync(dir, { recursive: true });
  writeFileSync(path.join(dir, "en.md"), fm + body);
  sync[slug] = { id: page.id, last_edited_time: page.last_edited_time };
  changed++;
  console.log(`[notion] wrote ${slug}/en.md`);
}

writeFileSync(SYNC_FILE, JSON.stringify(sync, null, 2));
console.log(`[notion] done. ${changed} changed, ${results.length} total Published.`);
```

## Consequences

**Becomes easier:**
- Authoring posts on mobile, with collaborators, with comments
- Vercel deploy stays at ~25-30s (no translator phase) — predictable
- Decoupling: Vercel deploys don't depend on Notion or AI Gateway uptime
- Drafts: posts in `Status: Draft` never appear; flip to `Published` to publish

**Becomes harder:**
- Editing markdown directly is now risky — next sync clobbers it. To edit: change in Notion, sync.
- One more piece of infra to monitor (GHA workflow). If the workflow fails repeatedly, you need to know.
- Notion → markdown conversion has edge cases (toggles, columns, embeds, mentions). Plan content with that in mind.

**Will need to revisit:**
- If publishing frequency exceeds ~1/day, evaluate webhook (Option B).
- If markdown fidelity from Notion proves poor, consider per-post `es.override.md` for ES + a similar `en.override.md` mechanism for EN (would require a tiny update to fetch-notion.mjs).
- The `translate-posts.mjs` script's "fall back to existing es.md if API down" branch becomes the primary path — i.e. if AI Gateway flakes during a GHA run, the post stays in ES from a previous run. Acceptable.
